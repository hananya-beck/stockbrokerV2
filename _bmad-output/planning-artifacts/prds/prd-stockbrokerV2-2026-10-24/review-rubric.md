# PRD Quality Review — Backtest simulator

## Overall verdict
The PRD is tidy and proportionate for a solo tool: explicit Non-Goals, three indexed assumptions, contiguous IDs and one named protagonist. What is at risk is how far the chart can be trusted. The Vision says the chart answers whether the score is worth trusting, but today's fixed weights are derived from trailing windows that overlap the backtested months, so the test is flattered by hindsight, and the PRD does not say so (a caveat inherited from the brief). Several FRs also leave the comparison undefined in gap months (holdings valuation, baseline redistribution) and leave the backfill mechanics unstated, so an engineer would have to invent rules before building.

## Decision-readiness — adequate
Decisions are stated as decisions: fixed suggested weights (§4.1 description, §5), a gross-of-fees result (§6.2), and no browser fetch (FR-7). The NOTE FOR PM in §6.2 sits on a real tension (a small fee gap could decide a close comparison), and OQ-1 and OQ-2 are genuinely open. Two things weaken it. First, dropping point-in-time recompute is presented as scope ("Deferred"), not as a loss: the PRD never says that the chosen test cannot tell whether the scoring method adds value over time (§5, §6.2). Second, UJ-1 promises "a start month two years back" while OQ-1 admits the history depth is unknown, and the PRD has no fallback or kill criterion if the source only returns a recent window.

### Findings
- **[high]** Point-in-time trade-off not named (§5 bullet 1; §6.2 bullet 1) — The PRD drops the one test that would speak to whether the scoring method added value over time, and records it as scope. A reader is not told that the MVP can only confirm or refute today's snapshot against history. *Fix:* Add one sentence to §6.2 stating what the MVP cannot tell the user.
- **[high]** History floor may make UJ-1 infeasible (§3 "History floor"; FR-1; UJ-1; §8 OQ-1) — Usefulness depends on how far back the source returns NAV, which is unknown, yet UJ-1 uses "a start month two years back" and FR-1 accepts any start at or after the floor. If the newest fund's series is short, the simulator runs but never serves the example journey, and nothing says what to do. *Fix:* Add a NOTE FOR PM naming the minimum useful history (e.g., 12 months) and the UI behaviour below it, and make reaching that floor part of FR-7's acceptance.
- **[low]** OQ-1 conflates floor and source depth (§8 OQ-1) — "How far back can the history floor go?" asks about the source, not the floor. *Fix:* "How far back does bizportal return daily NAV for each fund?"

## Substance over theater — strong
No personas, no differentiation section and no boilerplate NFRs. The Vision ("One chart answers the question that matters: is the score worth trusting, or is it no better than splitting evenly?") could not be pasted into another PRD. The two feature NFRs in §4.1 are concrete (no network request; bilingual strings). The one gap is absence rather than theater: §4.1 sets no run-time or payload bound, which is why OQ-2 cannot be closed.

### Findings
- **[medium]** No performance or payload bound (§4.1 Feature-specific NFRs; §8 OQ-2) — OQ-2 asks whether the stored history is "acceptable" for GitHub Pages, but nothing defines acceptable, and the browser-side run has no time bound. *Fix:* Add an NFR such as "stored NAV files total under N MB and a full run completes in under N s on the maintainer's machine," then answer OQ-2 against it.

## Strategic coherence — adequate
The thesis is clear: the score is unvalidated, so test it against history. Scope follows it: FR-1 to FR-5 serve the chart, and FR-6 and FR-7 are named as enablers (§4.2). The weak point is the test's validity. Today's suggested_weight is built from 1-, 3- and 5-year risk-adjusted scores ending today (brief, Problem section). Those windows cover the months being backtested, so the simulator applies weights chosen with hindsight to the very period that informed them, which likely favours the suggested split. The PRD does not mention this, and SM-C1 guards against tuning the weights, not against this bias. The framing of the Vision comes from the brief's success criterion and the scope choice is documented in the addendum, so the defect is a missing caveat rather than a missing thesis.

### Findings
- **[high]** Hindsight bias undisclosed (§1 Vision; §5; §7 SM-1) — The weights come from trailing scores as of today, and the backtest window overlaps the windows that produced them, so the suggested split is likely flattered against the equal split over that same period. The PRD presents the chart as an answer to "is the score worth trusting" with no caveat, so a user could trust a score the test cannot validate. *Fix:* Add a one-line caveat to §5 or a NOTE FOR PM stating the test is in-sample for the weights and cannot validate the score out of sample. No rewrite of the Vision is needed, though "whether today's split would have beaten an equal split over that period" would be the precise wording.
- **[medium]** SM-1 is a self-report, not a checkable bar (§7 SM-1) — "Hananya can read the chart and say whether ... with no extra steps" is neither verifiable nor a test of the thesis: a chart can be readable and still misleading. *Fix:* Keep SM-1 as a usability check and add a verifiable metric, e.g., "For a fixed NAV fixture, the final values of both lines match hand-computed values."
- **[low]** SM-C1 is a principle, not a measurable counter-metric (§7 SM-C1) — "The weights are not tuned to make the backtest look better" cannot be observed in the product. *Fix:* Make it a process rule, e.g., "the allocation formula is not changed in the same change set as backtest results," or drop it from the metric list and keep it in §5.

## Done-ness clarity — thin
This is the weakest dimension and matters most, since downstream stories will lean on it. The gaps are behavioural holes in gap months and in the backfill, which an engineer would have to fill with invented rules. FR-4 defines what happens to the month's deposit when a fund has no NAV, but not to the fund's existing holdings, and §3 defines "Cumulative value" as valued at "the month's last NAV", which does not exist for that fund that month. FR-3 splits the baseline "evenly across all 7 funds" and FR-4 redistributes only the suggested weight, so the PRD does not say whether the baseline's 1/7 is redistributed, held as cash or dropped. Since FR-5 requires both lines on the same deposit schedule, this decides whether the two lines are comparable in gap months. FR-7 states where code runs ("never in src/ or index.html") rather than what must be loaded, and it does not say what triggers the one-time backfill (§6.1 says one-time; FR-7 says "scheduled or manually dispatched") or what the user sees if the backfill is partial or fails (AGENTS.md requires failures to be shown). FR-2 is tested only by a flat-NAV case, which does not check the arithmetic at all.

### Findings
- **[high]** Holdings valuation undefined when a fund has no NAV (FR-4; §3 "Cumulative value") — FR-4 covers only the deposit. A fund's units have no "month's last NAV" in a gap month, so cumulative value cannot be computed as written. *Fix:* Add a consequence stating the valuation rule (e.g., carry the last known NAV forward and mark the month), and index it as an ASSUMPTION in §9.
- **[high]** Baseline gap behaviour unspecified (FR-3 vs FR-4) — FR-3 splits "evenly across all 7 funds" and FR-4 redistributes only the suggested weight, so the two lines can diverge for reasons unrelated to the score. *Fix:* Add a consequence to FR-3 saying how a fund's 1/7 share is handled when it has no NAV (same redistribution as FR-4, or held as cash), applied identically to both lines, and index the choice.
- **[high]** Backfill mechanics unstated, one-time vs recurring mismatch, no failure state (FR-7; §6.1) — §6.1 says "its one-time backfill", while FR-7 says the history "is loaded by a pipeline run (scheduled or manually dispatched)". There is no trigger or mode, no completeness rule (how far back, what counts as done), and no statement of what the user sees if the backfill returns less than the source has. *Fix:* Specify a backfill mode (e.g., a workflow_dispatch input), a completeness check that records the floor actually reached, and a visible failure state for partial or failed runs.
- **[medium]** Core arithmetic tested only by a flat-NAV case (FR-2 Consequences) — A flat-NAV test passes for many wrong implementations, including ones that ignore the weights. *Fix:* Add a fixture consequence, e.g., "Two funds, 50/50 weights, one ₪100 deposit: fund A NAV 100 to 110 and fund B 100 to 100 gives a final value of ₪105."
- **[low]** FR-4 consequence is not a checkable bound (FR-4 Consequences) — "A fund with NAV gaps does not lower the value of the funds that have data" depends on returns, so correct code can violate it. *Fix:* Replace it with a fixture: "With fund B missing in month m, fund A receives its proportional share of B's deposit and the final value matches the fixture."
- **[low]** Presentational terms undefined (FR-4 "mark that month"; FR-5 "distinct styles") — Neither the marker nor the two line styles is specified. *Fix:* Define the marker (e.g., a shaded band with a tooltip naming the missing funds) and the two line styles.
- **[low]** Partial current month undefined (§3 "Backtest range"; FR-2 assumption) — A month in progress may have NAV for every fund but not a month-end value, and the glossary does not say whether it counts as the latest month. *Fix:* Add a rule that the current calendar month is excluded until it closes, or index it as an ASSUMPTION.

## Scope honesty — adequate
Non-Goals (§5) and the MVP split (§6) are explicit, the fee deferral carries a NOTE FOR PM at a real tension, and the three inline ASSUMPTIONs roundtrip to §9. Open-items density (2 OQ, 3 ASSUMPTION, 1 NOTE) is proportionate for a hobby feature. The gaps are silent omissions: the in-sample limitation is absent (see Strategic coherence), and the "gross of fees" label that §6.2 relies on has no FR requiring it.

### Findings
- **[medium]** "Gross of fees" label promised but unrequired (§6.2 bullet 2; FR-5; §5) — §6.2 says "the result is labeled gross of both", but no FR-5 consequence requires the label, so the chart can ship without it while the simulated returns overstate both lines. *Fix:* Add to FR-5 Consequences: "The chart and the final values state that results are gross of fees and taxes."
- **[low]** Point-in-time framed twice (§5 bullet 1; §6.2 bullet 1) — §5 says it is never tested; §6.2 says it is deferred to v3. The memlog records that duplication was removed, but this one survived. *Fix:* Keep it in one place with a pointer from the other.
- **[low]** Brief fidelity: "start date" narrowed to "start month" without a record (FR-1 vs brief Scope "Pick a start date") — The change is not in the memlog. *Fix:* Record it as a memlog decision, or restore day precision if intended.

## Downstream usability — adequate
The glossary covers the main nouns, IDs are contiguous, cross-references resolve, UJ-1 has a named protagonist, and the Assumptions Index roundtrips (3 of 3). This PRD is chain-top, so the drift matters. Terms for the two lines and the weights drift: "equal split" (§1, SM-1), "equal-weight baseline" (§3), "equal-weight line" (UJ-1), "baseline" (FR-3); "suggested split" (§1, SM-1), "suggested allocation" (FR-2, UJ-1), "suggested weights" (§4.1, §5, §6.2), while the glossary defines only "Suggested weight" (singular, per fund). "Total deposits" (FR-2) and "total deposited" (FR-5) also differ.

### Findings
- **[low]** Glossary drift for lines and weights (§1; §3; FR-2; FR-3; UJ-1; SM-1) — The same concept is named several ways, so an extracted story could split one term into two requirements. *Fix:* Add "Suggested allocation" to §3 as the portfolio built from suggested weights, use "equal-weight baseline" throughout, and align "total deposits" wording.
- **[low]** Hard-coded fund count (§1; §3 "Equal-weight baseline"; FR-3) — "all 7 funds" conflicts with the add-fund skill, which changes the fund list. *Fix:* Use "every fund in `data/funds.json`" in §3 and FR-3, and keep "7" only as a description of today's set in §1.

## Shape fit — strong
A single named protagonist (UJ-1), a capability-spec FR structure and a length proportionate to a solo dashboard suit the product. Nothing is forced into a consumer, regulatory or multi-stakeholder shape. No findings.
