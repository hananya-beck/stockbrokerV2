### Findings by lens

**Adversarial** (`a9958b4389290d593`), **edge-case-hunter** (`a57e330d1e7ac9a6f`), **verification-gap** (`a51a1157bdef70c3e`). Findings that more than one lens raised are grouped under one ID.

**F1. Non-finite metric reaches `funds.json` (fix now).**
- Source: `scripts/fetch_data.py:416` writes `output_text` with `json.dumps(output, ensure_ascii=False, indent=2)`, with no `allow_nan=False`. The history write at `:415` has it. Adversarial F1, verification-gap F3, edge-case F2.
- Re-checked: a close of `NaN` in the series produces `last_price` `NaN` in the metrics, and the funds JSON text contains a bare `NaN` token. `index.html` parses this file with `JSON.parse`, which rejects it.
- Breaks the epic context rule "non-finite values fail loudly rather than being written" and the matrix row "non-finite serialization" as applied to funds.
- Origin: the missing guard predates Epic 1 (`3565b7ef`). Story 1.4 rewrote this line (`fb396f5`) and kept the guard off funds. Blocking for the verdict.

**F2. A negative close aborts the whole run (fix now).**
- Source: `scripts/fetch_data.py:385-387` computes metrics from the raw fetched series. `nav_points` (`:102-107`) filters non-positive closes for history only. `annualized_return` (`:196-201`) then returns a complex number for a negative base at 756 or more points. The sort at `:402-405` is outside the per-fund `try`.
- Re-checked: a 1300-point series ending at `-5` gives a complex score, and `funds.sort` raises `TypeError: '<' not supported between instances of 'float' and 'complex'`. No file is written, and the daily run fails.
- Breaks Story 1.1's I/O matrix row "Bad close: point dropped, the other points are kept, dropped without failing the run" (`spec-1-1-store-each-fund-s-daily-nav-series.md:31`). Blocking for the verdict.
- Origin: the split between history and metrics was introduced in Story 1.1 (`e2c0a04`). The sort and `annualized_return` predate the epic.

**F3. Fetched points are dropped when metrics fail (fix now, low likelihood).**
- Source: `scripts/fetch_data.py:385-387`. `series_by_id` is set after `compute_metrics`, so an exception in metrics sends the fund to the failure branch and today's points never reach the history.
- Edge-case F3, reported low confidence. Ordering re-checked in the code. Fixed by F2's single cleaned series if it is adopted.

**F4. Concurrent runs conflict on the generated files (fix now).**
- Source: `.github/workflows/update-data.yml` has no `concurrency` key. No workflow under `.github` has one. The commit step at `:29-32` runs `git pull --rebase` (added in `fb396f5`). The 05:00 UTC cron and a refresh-button dispatch can overlap.
- Edge-case F1 and adversarial F5. Re-checked: no concurrency key exists.
- Consequence: the second run's rebase conflicts on both data files, the push is skipped, and that day's refresh is lost. The add-fund skill's rebase step (`SKILL.md:18`) has the same exposure on a manual push.

**F5. Fund removal or rename silently deletes its history (defer, decision needed).**
- Source: `scripts/fetch_data.py:361-365` filters stored history to configured ids, and `nav_history_payload` writes only those (`:166-182`). Introduced in `8b91fa3`.
- Adversarial F3. The spec's "Fund left the config: not carried" row makes this deliberate. There is no warning and no archive.
- Decision for a human: archive orphaned entries, or warn and keep the drop. See Open questions.

**F6. A corrupt `nav-history.json` blocks every daily run (defer).**
- Source: `scripts/fetch_data.py:143-152` exits before any fetch when the history does not parse. This is the intended Story 1.3 behaviour.
- Adversarial F4. The skill's recovery path is a hand merge at `SKILL.md:18`, which can leave conflict markers. The recovery step is not documented anywhere.
- Defer: write the recovery into the skill (regenerate with `python scripts/fetch_data.py`, do not hand-merge).

**F7. A frozen source is marked fresh (defer, decision needed).**
- Source: `scripts/fetch_data.py:385-386` sets `"stale": False` on any successful fetch. Nothing compares the last date with the expected trading day.
- Adversarial F6. Not reproduced, since it needs a live frozen response. Recorded as a gap, not a defect.
- Decision needed: a trading calendar or a generous age margin. See Open questions.

**F8. Stale funds keep their score forever (defer, decision needed).**
- Source: `stale_metrics` (`:324-338`) carries the previous `risk_adjusted_score` into `allocate_weights` (`:291-321`) with no age bound. Introduced in `549cf06`.
- Adversarial F7. Decision needed: a maximum stale age after which the score is dropped. See Open questions.

**F9. The metrics window comes from the fetched response, not the stored history (defer, decision needed).**
- Source: `scripts/fetch_data.py:385`. `compute_metrics` receives the fetched window, while the history is merged from the store.
- Adversarial F9. A short response for one day can drop a fund from `long_horizons` to `partial_history` (the 0.5 discount) and move every fund's weight. The stored history is intact.
- Decision needed: whether metrics read the merged store. This conflicts with Story 1.2's intent. See Open questions.

**F10. Previous `funds.json` read swallows every error (defer, already tracked).**
- Source: `scripts/fetch_data.py:369-375`, a bare `except` that sets `previous = {}` for all funds at once.
- Adversarial F8. Already listed in `deferred-work.md`.

**F11. Killed write leaves temp files, and they are not ignored (fix now).**
- Source: `scripts/fetch_data.py:341-354`. A SIGKILL skips the `finally`, leaving `data/*.tmp`. `.gitignore` has no `data/*.tmp` entry.
- Adversarial F10. A `git add data/` could commit a partial JSON file.

**F12. Windows `os.replace` can raise mid-move (defer, low).**
- Source: `scripts/fetch_data.py:349-351`. A `PermissionError` on the second move leaves the new history beside the old fund list, the half-state Story 1.4 accepts by design.
- Adversarial F11. Local runs only, since the workflow commits only after success. Low likelihood.

**F13. The workflow tests check names, not behaviour (fix now).**
- Source: `tests/test_fetch_data.py:687-690` checks only that lines naming `data/funds.json` also name `data/nav-history.json`. `tests/test_fetch_data.py:693-697` reads the workflow as text. It checks that `git pull --rebase` appears before `git push` and that no `git push` line contains `||`.
- Verification-gap F1: a change that adds `continue-on-error: true` or `set +e` to the commit step would pass the tests while breaking Story 1.4's "fails the run when the push fails".
- Verification-gap F2: the fetch step (`:23`) and the commit step (`:25-32`) are not ordered by any test. Moving the commit above the fetch would pass.

### Process lessons (upstream)

- **P1. One cleaned input per fund.** Story 1.1 let the history and the metrics read different series, and that split produced F1, F2 and F3. Epics that split an input into an output path and a metrics path should name the single validated series both read from. Spec wording for future epics: "every output reads the same validated series".
- **P2. Workflow changes need behavioural tests.** The Story 1.4 test checked the text of the workflow, which is why F13 passed. Stories that touch a workflow should parse it and assert step order and failure policy.
- **P3. The orchestrator brief should pre-grant the files a story can touch.** Story 1.4 was blocked on `.claude/skills/add-fund/SKILL.md`, which its own acceptance criteria named. The brief should list every file an AC names, so the story session has permission to edit it.
- **P4. Commit-generated-files workflows need a concurrency guard.** See action item 7.

## Open questions

These are decisions a human needs to make. Each answer would change the code.

1. **F5 (fund removal):** should a fund dropped from the config have its history archived, or should the run warn and drop it? A warning-only fix is cheap. An archive changes the file shape.
2. **F7 (frozen source):** what counts as stale? Options are a trading calendar, or an age margin of N days. A calendar is exact but needs maintenance.
3. **F8 (stale score):** after how many stale days should a fund's score be dropped to the floor weight?
4. **F9 (metrics window):** should metrics be computed from the stored history rather than the day's response? This would protect the weights from a short response, but it changes what "the metrics" means for the page.
5. **Story 1.2 intent vs. the spec:** Story 1.2 says each run adds to the stored history. Does the spec also intend the metrics to read that history? The answer decides F9.
